Connect grants read access to the selected wallet. Signature verification is needed for private chat/history and server-owned intents; manual marketplace transactions may use the existing deterministic wallet preparation without a login signature, as in the functional console. Every broadcast still requires a separate explicit confirmation. No model-generated transaction data is accepted.

## Risk-based verification matrix

Before calling this ready, record outcomes for: initial disconnected/loading/empty/error/retry; canonical assets/listings/filter/sort/cursor reset; wallet connect/chain/account/session changes across routes; exact input and insufficient balance; approval vs action; rejection/stale/expired/double-click; receipt/reload/replacement; primary purchase/resale/claim/cancel/relist/settle/release; no mixed-account data; desktop/mobile keyboard/navigation; adjacent landing/chat; full pnpm check. Local/Anvil, mocked failure injection and hosted read evidence must be distinguished. Browser signatures and testnet broadcasts remain separate from scripted local evidence.

## Implemented boundaries

- Product routes no longer import `preview-data.ts`. The unrouted preview components from the original slicing remain as reference; landing and design-system illustrations remain intentional examples.
- Shared identity and receipt tracking cover all product routes. Claims use current chain balances when connected to the correct network; positions use canonical indexed pages plus newer verified receipt snapshots. Unknown data is never a fabricated zero or a summed USD portfolio value.
- The activity journal covers this browser only. It is not a complete wallet explorer. Reload verifies saved hashes; it does not rebroadcast. Account/network changes clear reviews and financial drafts.
- MKT-004 is preserved: expired, uncancelled OFFERED positions can relist; cancelled primary positions cannot. Cancellation can target an expired current listing. ACTIVE positions must settle before backing release; CANCELLED positions release after safe coverage without a settle transaction. Every action is simulated again by the existing wallet engine.
- Encoded canonical route keys are decoded once and checked against this deployment. Old chat links redirect to the same detail. Display fixture IDs do not resolve to financial entities.
- The duplicate-claim runtime regression exposed distinct viem class instances across workspace peer dependencies. Revert decoding now walks bounded known error envelopes; RPC failures remain failures, and unknown explicit reverts return a bounded code.

### Chrome wallet follow-up

The connected Chrome wallet restored its identity after refresh and retained the same account across wallet, portfolio and create-listing routes. The create form read real registry token balances, rejected backing above the balance, and produced a review matching the selected asset, amount, price, share and term. No transaction was sent.

The IP-literal preview exposed an actual login failure: native Supabase returned `validation_failed` / invalid SIWE domain. A controlled invalid-signature probe isolated the domain validation before any successful authentication. The preview now uses `http://localhost:3017` with matching `APP_ORIGIN`. Authentication rejects configured IP-literal origins before creating a challenge, and wallet UI errors explain optional verification instead of showing only raw codes. Localhost and named HTTPS deployments remain strictly origin-bound.

Native authentication and RLS regression passed again on isolated local Supabase with its existing allowed `localhost:3000` origin: valid/invalid signatures, concurrent single-use challenge, replay bypass rejection, foreign-chain session rejection and revocation. An initial attempt using port 3017 was rejected by that local provider's URI allowlist; no provider permissions were broadened to make the test pass. The browser preview and isolated provider checks are separate evidence.

Wildan confirmed the Verified badge on the corrected preview. This is user-reported manual evidence. Subsequent automation lost Chrome control, so authenticated refresh, account/network switching, approval/action confirmation and persisted receipt UI are still open gates. No claim of hosted deployment or completed financial browser acceptance is made. Follow-up check counts and the tested revision are recorded in the PR.
